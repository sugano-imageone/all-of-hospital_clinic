## 月次自動取得

[GitHub Actions](../.github/workflows/notifications-monthly.yml) は、毎月20日・25日の日本時間09:20に開始予定。GitHub側の混雑により開始が遅れる場合がある。

- 20日：8局・支局の全件医科名簿を公式ページから取得し、検証した局ごとにSupabaseの全件スナップショットを入れ替える。同月成功済みの局は再実行しない。
- 25日：Supabaseの当月20日の状態を参照し、失敗・未完了の局だけ再取得する。20日の状態がなければ停止する。
- 初回投入は `production.py --bootstrap-index ...` で明示的に行い、将来の20日の成功記録を生成しない。
- 未完了のバッチは検索対象から隔離する。県範囲、施設カバレッジ、最新判定、件数、日付、前回比の検証後に同一トランザクションで局の採用先を切り替える。取得・検証・転送失敗時は採用先と基準日を変更しない。
- 月次状態はDBに永続化する。原本・URL・SHA256・検証記録はActions artifactに90日保存する。前回の検証済みDBスナップショットを復旧用に残す。
- 既存の医療機関マスタ更新workflowは変更しない。秘密キーはActions Secretsから取込プロセスだけへ渡し、公開Pagesへ含めない。

## 同一医療機関・同一項目の最新情報

医療機関コードと正規化した正式名称ごとに、受理日が公表されている場合は「受理年月日」または「受理日」を優先する。今回取得した全47シートと各局・支局の代表PDFを再確認したところ、全件名簿の日付は「算定開始年月日」だった。2026年10月19日のユーザー指定に従い、受理日がない場合はこの算定開始年月日を比較基準にする。算定開始日を受理日へ読み替えたり、受理番号やExcelの行順を新旧の根拠にしたりしない。個別有効開始年月日は情報として保持し、同じ算定開始日の新旧を断定するためには使わない。

選択後は1,003,929医療機関・項目組。古い明細2,782行を検索対象から除外した。同一届出の複数の備考行は1件へ統合し、内容を保持する。

同じ最新日付で複数受理番号がある組は、検索上は1組にまとめつつ、複数原文と `same_date_multiple_receipts` フラグを保存する。公開データだけでは1番号へ絞れないため、任意の1件を最新と断定しない。受理日のある版と受理日が欠けた版が混在して比較不能な組は、日付の種類を混ぜずに未解決として保持し、その局の入れ替えを止める。比較基準と解決状態は `date_basis`、`latest_selection_resolved` に記録する。

## 検索仕様と実装範囲

通知条件のON/OFFと届出有無の検索処理は `scripts/facility_notifications/query.py` に実装・試験した。本番統合は `018_notifications.sql`、`production.py`、既存のPagesクライアントに追加。採用状況はリリース記録を参照。

1. 「届出事項を検索に利用する」の初期値はOFF。OFFでは保存済みの項目・有無条件を適用せず、届出テーブルも参照しない。
2. ONにした場合は正式名称の項目を選択し、その後に「届出済の」「未届出の」を選択する。画面には「未届出」と表記する。
3. 「届出済の」は該当項目がある現存施設、「未届出の」は取得済み名簿にその項目がない現存施設。局の取得済みだけで判断せず、施設自体が取得済み名簿に載り、当該局に選択項目が存在することも確認する。施設の存続状態と母集団は厚生局の医療機関マスターで判定する。届出名簿に過去の施設名が残っていることだけを理由に現存施設へ追加しない。
4. 未取得の局、存在しない項目名、データ未取得を「未届出」に変換しない。結果には対象名簿の基準日を添える。「未届出の」はその公表名簿に掲載がないという意味であり、現在まで未提出と断定するものではない。

### 検索欄の下の基準日表示

2026年10月19日追加仕様。検索条件フォームの直下、検索結果の手前に「検索に使用するデータの基準日」を常時表示する。届出事項の検索がOFFの場合や検索実行前も表示し、利用者が検索に使うデータの時点を確認できるようにする。画面は採用メタデータRPCから取得し、固定値で基準日を表示しない。

- 北海道厚生局、東北厚生局、関東信越厚生局、東海北陸厚生局、近畿厚生局、中国四国厚生局、四国厚生支局、九州厚生局の8行を正式名称で表示する。検索地域の選択にかかわらず8行を表示し、中国四国厚生局と四国厚生支局を分ける。
- 表は「厚生局・支局」「医療機関データの基準日」「届出事項データの基準日」の列を設ける。両者の基準日が異なる場合も混同せず、それぞれ実際の値を表示する。日付の表記は `2026年10月1日` の形式とする。
- 基準日は現在検索に使う、取得・検証・取り込み済みデータの公表基準日を表示する。ページ更新日、取得日、今回の取得試行日を代わりに使わない。表示用の日付を固定値にせず、局ごとのデータ入れ替えと同時に更新する。
- 20日の取得・検証に失敗した局も、保存済みの最新データの基準日だけを表示する。「前回データを保持」などの注記は付けない。25日も失敗した場合は同じ基準日を表示し、成功した局だけ新データとその基準日へ切り替える。
- 例：保存済みの最新データが9月1日基準で、20日の10月分取得に失敗した場合は「2026年9月1日」と表示する。20日という試行日や、まだ取り込めていない10月1日へ書き換えない。
- 一度も取得できていないデータは「未取得」と表示し、推測の日付を入れない。局内で県によって基準日が異なる場合は、県別の基準日を確認できる表示にする。

医療機関データと届出事項データは、それぞれ保存済みの最新データに対応する基準日を表示する。

### 取得ログの確認

2026年10月19日追加仕様。取得ログの確認は、マスタ権限者から明示的に求められた場合のみ行う。一般の管理者・閲覧者をログの確認対象に含めない。検索フォーム・管理画面へのログ表示、ログ閲覧フォーム、常時表示や自動通知は追加しない。

問い合わせに応じて、保存済みの取得ログから対象の年月・局の取得日時、成功・失敗、検証結果、実際に採用したデータの基準日を確認して提示する。マスタ権限者であることを既存の認証・権限で確認し、表示名や自己申告だけで権限を判断しない。保存期間を過ぎたログなど、記録がない情報は推測で補わない。

閲覧者がツールで行った検索・出力などの履歴は、別途 [閲覧者の利用履歴](viewer-usage-history.md) の仕様で管理者・マスタに提供する。取得ログをマスタのみとする扱いは変えない。

## 再現方法

Python 3.12、httpx 0.28.1、beautifulsoup4 4.14.2、openpyxl 3.1.5、poppler-utilsが必要。

```sh
python scripts/facility_notifications/collect.py --output work/notifications-initial
python scripts/facility_notifications/build_index.py --input work/notifications-initial
python scripts/facility_notifications/latest.py --database work/notifications-initial/medical-notifications.sqlite
python scripts/facility_notifications/search.py --database work/notifications-initial/medical-notifications.sqlite --name '医療安全対策加算１'
python -m unittest discover -s scripts/facility_notifications -p 'test_*.py'
```

27件の試験が成功。受理日と算定開始日の新旧が逆転する例、受理日が一部欠けた例も試験した。取得済みの公式8ページから全件URLを再解決した結果も初回取得URLと一致。実データで正式名称検索を実行できたことを確認した。将来の公式サイトの形式変更まで保証する検証ではない。
