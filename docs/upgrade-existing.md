012を適用済みでも実行できます。012の安全更新チェックへの修正を含み、データ送信を小分けにして最終的な県別登録は一括のまま維持します。
一般利用者の制限・権限・RLS、県別取込の一括ロールバックは維持します。

## 変更内容と保持するもの

- テーブル削除・再作成・個票の物理削除は行わない。
- 施設のUUID、取込ID・変更履歴IDのbigint identity、既存の外部キー・索引を維持する。
- 医療機関コード・名称などの列をアプリの列名へ統一する。列名変更は既存クライアントのAPI契約に影響するため、このリポジトリの更新と組み合わせて適用する。
- `viewer` → `user`、`enabled` → `approved` に変換し、既存の有効・無効状態は保持する。新しい利用者の既定値は未承認にする。
- 英語の施設状態を日本語へ対応付けて変換し、「休止」を追加する。英語の病院／診療所区分も日本語へ統一する。
- 取込状態の`completed` → `success`に変換する。既存の取得日（date）は保持し、正確な取得時刻が不明なら新しい時刻列をNULLにする。
- 元の診療科目文字列は文字列要素を持つJSON配列として保持する。
- 現在の病床表は横持ち・施設ごと1行のまま維持する。検索用の病床値を同期し、取込ごとの病床履歴を新テーブルへ追加する。
- 元の変更履歴のコード・種別・確認状態・根拠を保持し、観測イベントを追加する。確認済みの既存履歴だけを対応する集計に含める。
- 管理者限定だった取込履歴・変更根拠の直接閲覧制限を維持する。承認済み一般利用者には、専用RPCから取得元の安全な項目と月次件数だけを返す。
- 利用者管理RPC、アクセス履歴、コード関連、月次ジョブ、取込RPCを追加する。

全体を1トランザクションで適用します。想定外の構造・独自トリガー・制約違反があれば中止します。
成功済みの同じ移行を再実行した場合も、変更せずに適用済みエラーを返します。
SQL Editorへ独自のBEGIN/COMMITを追加せず、ファイル全体を実行してください。

## 検証

- 提供定義をそのまま隔離DBへ復元し、既存行を入れた状態から移行して、UUID・整数ID・病床数・変更根拠が維持されることを検証。
- 同じ取込・権限テストを新規スキーマと既存スキーマの両方で実行。
- 010の全文を別の隔離DBで実行し、九州8県の実データ11,661施設・現在病床11,661行・病床履歴58,305行を保存。
- 初回取込の誤った新規指定カウントは0件。
- 取込失敗時のロールバック、件数激減防止、消失時の廃止未確定、再実行、本人の権限昇格拒否、管理者限定履歴、一般利用者向け集計RPCを検証。

011全文の実行を移行済みの隔離DBで確認しました。PostgREST 13.0.7でも、サービスロールの制限を50msにすると200msの処理が57014で中止し、2秒に変更・設定再読込すると成功することを確認しました。
関数内の `SET statement_timeout` では開始済みのリクエストの制限を延長できないことも確認しています。
取込CLIのHTTP待ち時間は110秒で、DBの90秒より長くしています。

013ではSupabaseの `UPDATE requires a WHERE clause` に対応し、一時表の更新も当該取込IDへ限定しています。
大きいリクエストが認証中継で拒否される例もあったため、最大500件・約2MiBで送信します。
一時保管は一般利用者に非公開で、全件がそろうまでマスターに反映しません。
隔離DBと実PostgRESTを使い、東京都13,960件を小分け送信・一括確定・重複スキップできました（全体約23秒）。本番の最後7都府県48,170件の送信・確定は合計約5分32秒でした。全国の月次定期実行全体の受入検証は未実施です。
